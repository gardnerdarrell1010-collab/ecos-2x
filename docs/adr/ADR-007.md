# ADR-007 — Provider commands and idempotency/reconciliation

**Status:** Accepted Phase 0 design; channel authorization remains explicit owner policy.

**Context:** A provider may succeed while result persistence fails. A retry can duplicate a send.

**Decision:** Persist stable command identity/key/hash before effects; append attempts/results.
Unknown outcomes require provider reconciliation or human decision before any re-send.

**Rationale:** Database fences cannot cancel an already executing remote request. Native provider
idempotency must be verified, including key scope/expiry, rather than assumed.

**Alternatives considered:** Retry every timeout; claim exactly-once transport; allocate new key
on each attempt. All can duplicate externally consequential effects.

**Consequences:** Per-provider evidence and lookup strategy; unresolved ambiguity can block that
command while unrelated work proceeds. Permanent validation failures dead-letter for review.

**Portability impact:** Generic command/attempt/result contracts, replaceable provider adapters.

**Acceptance implications:** EV-02 provider-success/DB-failure and ambiguous timeout; EV-03
duplicate webhooks. Stable keys survive executor replacement and restore.
