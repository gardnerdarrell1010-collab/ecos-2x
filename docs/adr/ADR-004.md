# ADR-004 — Business Task separated from executable work

**Status:** Accepted Phase 0 design.

**Context:** The review's 80-column Task model mixes obligation and runtime bookkeeping.

**Decision:** task represents an obligation. Work definitions/stages/occurrences, claims and
runs represent execution. project_id remains nullable. Multiple stage types can fulfill one task.

**Rationale:** Runtime retries/handoffs should not manufacture new obligations or corrupt ownership.

**Alternatives considered:** One Task per stage; retain all runtime fields on Task. Both conflate
business reporting with dispatcher state.

**Consequences:** Explicit relationships, separate lifecycle fields, immutable stage evidence and
completion conditions; human waits do not retain a long-lived executor claim.

**Portability impact:** Relational separation works with any executor or UI.

**Acceptance implications:** TASK-01 validates independent tasks, multi-stage fulfillment and
schema rejection of lease/rank/attempt fields on task. TASK-02 covers cycles and schedules.
